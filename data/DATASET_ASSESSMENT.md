# Dataset Assessment — `synthetic_returns_dataset_csv.xlsx`

**Analysed 4 August 2026 · 5,000 rows × 14 columns**

This dataset was uploaded during the final merge. Because the entire project has
turned on being precise about what is and isn't real machine learning, it was
analysed before being used for anything.

---

## Summary

| Question | Answer |
|---|---|
| Can it retrain the cost prediction model? | ❌ **No** |
| Can it verify the unexplained R² = 0.9993? | ❌ **No** |
| Does it contain fraud labels? | ✅ **Yes — 303 positives (6.06%)** |
| Can it train a supervised fraud model? | ⚠️ **Technically yes, but see the warning** |
| Should the fraud model be deployed from it? | ❌ **No** |

---

## 1. It cannot train or validate the cost model

The deployed XGBoost model needs 15 features. This dataset has **2 of them**.

| Model needs | Present? |
|---|---|
| `return_reason` | ✅ (different vocabulary) |
| `customer_return_rate` | ✅ |
| `product_value`, `actual_weight`, `volumetric_weight`, `chargeable_weight` | ❌ |
| `courier`, `payment_mode`, `category` | ❌ |
| `pickup_tier`, `destination_tier`, `distance_km` | ❌ |
| `fragile`, `festive`, `merchant_return_rate` | ❌ |

**There is also no cost target column at all.** No processing cost, no logistics
cost, nothing the model predicts.

**Consequence:** the R² of 0.9993 in `model_metadata.json` remains unverifiable.
Known Issue KI-009 stays open. Do not quote that figure.

## 3. How the labels were generated — and why it matters

The dataset contains `fraud_risk_true`, a probability column. Testing whether
`is_fraud_flag` is simply a threshold of it:

| Risk band | Rows | Observed fraud rate | Mean `fraud_risk_true` |
|---|---:|---:|---:|
| 0.00–0.05 | 1,680 | 0.033 | 0.028 |
| 0.05–0.10 | 1,668 | 0.067 | 0.073 |
| 0.10–0.15 | 671 | 0.116 | 0.120 |
| 0.15–0.20 | 122 | 0.172 | 0.167 |
| 0.30–0.60 | 80 | 0.412 | 0.408 |

The observed rate tracks the mean probability almost exactly in every band.
Point-biserial correlation is 0.254 — moderate, not deterministic.

**Conclusion: `is_fraud_flag` was sampled as `Bernoulli(fraud_risk_true)`.**
The labels are stochastic, which is realistic in shape. But `fraud_risk_true` is
the *generating parameter*, and it sits in the dataset.

### Two consequences

**Leakage risk.** If `fraud_risk_true` or `approval_probability_true` are used as
training features, the model achieves near-perfect scores by reading the answer.
This is very likely the same mistake that produced the unexplained R² = 0.9993 on
the cost model. **Both columns must be dropped before any training.**

**Ceiling.** Because the labels are noisy draws, the maximum achievable AUC is
bounded by the generator, not by model quality. A high score here would mean the
model recovered the simulator's formula — nothing more.

---

## 4. Recommendation: do not ship a fraud model trained on this

This is exactly the scenario flagged in Phase 4:

> "the only way to do it would be to generate synthetic labels myself — which
> means the resulting 'ML model' would just be learning to reproduce the same
> if/else rules it's replacing, dressed up as a trained model. That would be a
> worse version of the exact mislabeling problem we caught in Phase 1."

A model trained on synthetic data learns the **data generator**, not real-world
fraud. Deploying it and describing it as "AI fraud detection" would undo the
central correction of this entire project.

The rule-based fraud engine stays. `AI_TRANSPARENCY.md` stays accurate.

### What this dataset IS legitimately good for

| Use | Value |
|---|---|
| **Development and demo seeding** | Realistic-looking data for demos without exposing real customer records |
| **Testing the label-capture pipeline** | Verify `PATCH /returns/{id}/outcome` and `train_fraud_model.py` end to end |
| **Rehearsing the training workflow** | Prove the pipeline works before real labels arrive |
| **Load testing** | Realistic data volume and distribution |

All four are real value. None of them involve claiming the fraud scoring is ML.

## 5. Open question for the Directors

**Where did this data come from?** The answer changes the recommendation:

| If it is… | Then |
|---|---|
| Generated by a script (most likely, given `*_true` columns) | Use for dev/demo/testing only. Recommendation above stands |
| Real merchant data, anonymised | **This changes everything** — a fraud model becomes genuinely trainable, and DPDP obligations apply immediately |
| Sourced from a public dataset | Check the licence before shipping it in the repo |

The presence of `approval_probability_true` and `fraud_risk_true` — ground-truth
generating parameters that would never exist in real operational data — makes
synthetic generation almost certain. But it is worth confirming rather than
assuming.

---

## 6. Actions taken

- Dataset stored at `data/synthetic_returns_dataset.xlsx` with this assessment
  alongside it
- **Not** used to retrain any model
- **Not** used to alter any claim in `AI_TRANSPARENCY.md` or `MODEL_CARD.md`
- KI-009 (unverified R²) remains open
- Fraud and damage scoring remain documented as rule-based
